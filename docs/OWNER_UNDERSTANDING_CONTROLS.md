# Explicit owner understanding controls

The owner can define vocabulary and state a preferred collaboration pattern.
These local declarations supply owner-authored information; they do not grant
execution authority or establish psychological conclusions, VAN capability, or
provider accuracy. They are visible in the existing understanding read surface.

## Device and session binding

Reads require the current bound owner device. Each PUT requires the ingress and
device credentials, a valid single-use hardware-bound HTTP request proof, and
`van_session_id` plus `session_epoch` for that device's current ACTIVE owner
session. The session, device revocation and active binding are rechecked within
the value/provenance write transaction. A machine understanding token cannot
substitute for the owner. The frontend does not automatically replay PUTs.

## Vocabulary

`PUT /v1/understanding/vocabulary` accepts exactly:

```json
{
  "van_session_id": "vhs_current-session",
  "session_epoch": 1,
  "term": "full implementation",
  "owner_meaning": "Every declared feature works with visible error behavior.",
  "system_operationalization": "Verify each required feature's effect and failure state.",
  "examples": ["Provider readback confirms the actual effect."],
  "anti_examples": ["An interface without an executable producer."],
  "project_id": "van"
}
```

Term length is 1–128, trimmed, lowercased and internal whitespace collapsed.
Meaning and operationalization are nonblank text of at most 4,000 characters.
Examples and anti-examples have at most 16 nonblank items of at most 512
characters; duplicate items are removed. A missing/null project is global;
otherwise the normalized project must be an exact configured project ID.
Confidence and evidence references are generated by the server. Confidence
1.0 means confidence in this explicit declaration, not proof of task success.
`is_operational` reports whether the definition includes operationalization and
anti-examples; an empty anti-example list is allowed and remains visibly false.

`GET /v1/understanding/vocabulary?term=...&project_id=...` reads that exact
scope. It returns 404 when absent, without falling back to the global definition.
The existing conversational resolver may use project-to-global fallback and
now applies the same term whitespace/case normalization. GET without parameters
returns `{ "entries": [...], "execution_grant": false }`.

## Collaboration preference

`PUT /v1/understanding/complement/preferences` accepts exactly:

```json
{
  "van_session_id": "vhs_current-session",
  "session_epoch": 1,
  "domain": "trading.analysis",
  "preferred_collaboration_pattern": "State uncertainty before proposing a change."
}
```

The pattern is nonblank text of at most 4,000 characters. Domain length is
1–128, trimmed and lowercased, with the finite syntax
`[a-z][a-z0-9_-]*(?:\.[a-z][a-z0-9_-]*){0,7}`. Wildcards and path syntax are
invalid. This domain labels collaboration context; it creates no domain
autonomy grant. The writer changes only the collaboration preference and
preserves separately inferred strengths, vulnerability candidates, task evidence
and confidence. Those inferred fields cannot be supplied or confirmed by this
writer. The complement entry ID remains stable on a domain update.

`GET /v1/understanding/complement/preferences?domain=...` returns the exact
preference or 404. GET without parameters returns the same list wrapper as
vocabulary. This is a declaration/inspection contract, not independent proof
that every future assistant response follows the preference.

## Committed readback and provenance

PUT and exact GET return:

```json
{
  "entry": { "domain": "trading.analysis", "entry_id": "ccm_example", "preferred_collaboration_pattern": "State uncertainty before proposing a change.", "evidence_refs": ["owner-memory://omd_example"] },
  "provenance": {
    "state": "OWNER_CONFIRMED",
    "source": "OWNER_AUTHORED",
    "write_id": "omd_example",
    "evidence_ref": "owner-memory://omd_example",
    "device_id": "bound-device",
    "van_session_id": "vhs_current-session",
    "session_epoch": 1,
    "recorded_at_ms": 1,
    "content_sha256": "sha256-of-canonical-declared-fields"
  },
  "execution_grant": false,
  "status": "SAVED"
}
```

Vocabulary entry fields are `term`, `project_id`, `owner_meaning`,
`system_operationalization`, `examples`, `anti_examples`, server `confidence`,
`evidence_refs` and `is_operational`. The owner preference projection exposes
only the fields in the complement example. `OWNER_CONFIRMED` applies only to
the exact declared content covered by the persisted digest.

The server commits value and provenance together, then reads the committed
target through a new connection. A concurrent replacement yields 409
`owner_memory_write_superseded`. The frontend performs another exact GET and
compares the write ID, digest and declared fields before displaying saved.
Existing inferred entries, or content that no longer matches a declaration,
are `status: OBSERVED` with `provenance.state: UNCONFIRMED`. Missing responses
remain unknown until an independent read resolves them.

Invalid/extra fields return 422; missing or changed device proof returns 401;
an unbound or wrong owner/session returns 403; a stale epoch or non-ACTIVE
session returns 409. Unknown configured project and absent targets return 404.
Read responses are `Cache-Control: no-store`.

The existing approved owner-memory erasure path now includes
`cognitive_complement_map` and removes declaration witnesses with vocabulary
or complement deletion. Audit and erasure evidence remain intact.
