# Immutable funding intent drafts

Candidate source component of BE-007. Provider funding operations and whole-unit, native, production and owner acceptance remain unissued.

BeneficiaryRef, PaymentFee, PaymentQuote and PaymentIntent reuse the existing exact Money owner. A draft binds provider/realm, owner/account scope, original quote and beneficiary-reference digests, amount, all included/additional fee assets, quoted debit, conversion reference, reference text, quote revision and half-open validity window. No exchange rate, beneficiary verification or entitlement is inferred from a digest. The full intent hash also binds the original request and DEPOSIT/WITHDRAW/TRANSFER operation. Changing a fee, scope, beneficiary, source, expiry, operation or request changes the binding. Strict wire readback rejects unknown fields, approval states, qualification flags and numeric substitutes for JSON booleans or integers.

PaymentDraftBook stores immutable unapproved inputs through the existing VATI SQLite/PostgreSQL ledger and PAYMENT_DRAFT event kind. It checks journal integrity and bounded history, serializes original-owner/request publication, checks expiry again inside the SQL writer, and reads the original committed receipt afterward. Lost acknowledgements remain unknown until that original request is independently read. Expired replay returns historical draft completion without renewing quote time or granting financial permission. Caller-owned writers cannot become committed evidence. The composition owner must supply its retention guard; the gateway reuses the existing payment-instrument policy for free text and identifiers. Typed money integers and clocks are numeric data, and fixed digest references are content references; neither is a stored payment method. No instrument fields are accepted. This does not qualify provider privacy, retention/erasure or a production migration.

The paired-owner gateway exposes POST `/v1/trading/funding/drafts`, GET `/v1/trading/funding/drafts/{request_id}` and GET `/v1/trading/funding/drafts/{request_id}/receipt`. Existing bound-device request proof applies to the write. It is a draft write, not a fresh A4 payment approval. Reads perform no provider operation. Existing account funding operations remain NEEDS_PROVIDER_ADMISSION/UNSUPPORTED. Responses retain versioned original exact values, DRAFT_STORED_NOT_APPROVED and current payment eligibility NOT_ADMITTED. No query-supplied owner, ledger path or policy is accepted. Private errors do not reflect rejected input. Two original worker slots remain occupied across request cancellation; a disconnected caller does not undo an original write. The encoded request limit is512KiB and ambiguous JSON refuses; this is not a host RSS/CPU/latency qualification.

The native ledger must already be provisioned; an absent or in-memory store refuses rather than claiming durable storage. Connections are created and closed inside their actual workers. No backend address or filesystem setting is requested from the phone. Deployment and production-profile provisioning are separate. The new event kind requires compatible readers across the admitted cohort before activation; source construction is not a rolling-upgrade or rollback qualification.
