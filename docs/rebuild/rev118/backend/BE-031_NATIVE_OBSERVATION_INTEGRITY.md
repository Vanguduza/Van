# Native MT5 observations and uncertain SDK effects

The Windows worker now distinguishes successful empty native collections from failed observations. Missing or malformed position, order or deal-history collections produce unavailability. They no longer become `[]`, which could incorrectly describe a flat account or an empty financial history. A cached account identity also needs a current explicit terminal connection; offline, missing or non-boolean connection facts cannot establish a verified broker view.

Entry permission includes explicit account trading, account expert trading, terminal algorithmic trading and Python trading-API flags. Unknown flags do not permit an entry. A permission denial does not disable connected read-only observations or remove existing protection. These native checks remain separate from signed owner policy, Linux profile binding, current issuer and lease fences.

An SDK return of `None` after an entry, stop modification or close cannot establish no effect: the request may have reached the broker before its reply was lost. The worker retains UNKNOWN outcomes, and the adapter does not manufacture stop confirmation for an unknown close. The tests execute the SDK fixture's effect first, then discard its reply, and check the actual retained position/stop state against the uncertain receipt. This is a source counterexample, not a claim that a live broker trade was performed.

Native partial-close retcodes remain PARTIAL with the reported fill quantity. An incomplete close is not promoted to a complete fill. Successful empty reads, known refusals, valid entries and protective operations retain their ordinary paths. Later native financial finality, correction events, deferred execution envelopes and original-operation reconciliation remain the original execution requirements; uncertainty is not resolved by a new send.

`receipts/MT5_OBSERVATION_INTEGRITY_SOURCE_20261023.json` binds the tested source, original failures, staged protection-confirmation correction, affected worker/factory/physical-identity/client tests, the full trading/recovery selection, private PostgreSQL cleanup and ten introduced regressions with passing baselines and restored source. The real mTLS/HMAC application code runs against an isolated SDK fixture. No broker execution, whole-unit, deployment, profitability, independent certificate or S24 acceptance is issued.
