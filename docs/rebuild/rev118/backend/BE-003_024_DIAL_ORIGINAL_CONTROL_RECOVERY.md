# Original DIAL control recovery

The DIAL Android reducer previously called every HTTP 503 “not sent” and every 409 “stale view.” A lost reply could therefore offer a new idempotency key. The existing UI also rebuilt retries from current parameters and projection revision, and lost its pending identity on process recreation. Three reproduced Kotlin failures and a missing gateway action-read route established these gaps.

The existing control flow now records the prepared request in Android encrypted preferences before dispatch. It retains the original parameters, target, revision and key across retries, client instances and process recreation. A changed instruction for the same control and native target cannot replace unresolved work. Distinct typed owner controls, including protective pauses, remain subject to native authorization. Failed or corrupt storage refuses dispatch. No proof, token, endpoint or native credential is persisted in this record; private prepared guidance is removed after a bound terminal read. Recreated screens issue reads, never automatic POSTs.

`GET /v1/dial-dev/actions/{action_id}` relays DIAL's existing exact action projection under the current owner authentication and native transport checks. Android uses it to reconcile an action independently of bounded recent-action lists. Missing, unavailable, stale, malformed or foreign readback retains the original. A known terminal action must match its action ID, kind and project/task/decision scope. APPLIED also requires the matching native tool and its acknowledgement fields. A controlled probe of pinned DDS `callBridge` showed empty HTTP200 JSON returned `ok:true,result:null`; the consumer refuses that unsupported result. Recent metadata cannot bypass the bound read, and earlier observers cannot erase a newer request or report its result as the newer control.

Ambiguous transport failures retain the original key. Only an explicit native `STALE_VIEW` response releases a prepared request as not admitted; a local idempotency conflict does not. Native `CONTROL_*`, `NO_TYPED_CONTROL` and forwarder error reasons remain unresolved because a previous attempt may have reached the control service. The app does not treat those reasons as proof that nothing happened. Supersession is reported as supersession, and an applied control is separate from task success.

The pinned DDS implementation hashes action, target and parameters for native idempotency and checks an existing key before the projection-revision comparison. That permits an exact original retry with a fresh verified device proof. Native project/task truth remains in DDS; this change creates no parallel task registry or new planner and introduces no redesigned screen.

The upstream source still needs independent adjudication for an uncertain native control whose forwarder has already recorded rejection. This consumer preserves and blocks replacement of that original rather than inventing a no-effect certificate. Live service credentials, native gates and S24/Artemis acceptance remain separate. Source, persisted-state, TLS, Kotlin, Android build and deliberate-fault evidence are recorded in `receipts/DIAL_ORIGINAL_CONTROL_SOURCE_20261023.json`.
