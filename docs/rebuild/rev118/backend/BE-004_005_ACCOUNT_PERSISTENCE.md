# BE-004/005 candidate: account and credential mutation persistence

The existing account registry and Commander account handlers now serialize local state changes. This is a partial source milestone in the original programme, not account/provider admission, safe exposure qualification, credential verification or completion of either unit.

Six original counterexamples showed that a stale registry instance could lose a disjoint account, overwrite a newer label, delete another account while removing its target, or overwrite a concurrently created alias. A spawned-process rendezvous reproduced two successful additions leaving only one persisted account. Atomic file replacement alone did not protect the read/modify/write operation.

Every registry mutation now reloads under a persistent sidecar file lock. Disjoint edits merge; changes to the same account since the caller's read refuse and require reload. Direct whole-file saves use a baseline comparison and cannot bypass the protection. A malformed persisted registry stays unresolved rather than being overwritten from a stale cache. Failed swaps preserve the previous file and local cache. All account identities are validated, and string/integer substitutes for `demo`/`enabled` refuse. The actual Commander handlers also reject ambiguous JSON environment flags before record or credential changes.

Two further counterexamples reproduced credential key loss and absence of an atomic replacement boundary. Credentials now merge and replace under a separate persistent lock with an owner-only temporary file, flush/fsync, and atomic rename. Failed rename retains the complete previous active file and removes its temporary file. Invalid multiline values, non-private old files and a symbolic-link destination refuse. Values remain absent from public results and audits. This establishes local file persistence; it does not verify a new credential with a provider or claim storage-controller/power-loss qualification.

The actual mutating Commander handlers share an account-level lock acquired before their account lookup. This prevents a waiting rotation from recreating secrets after a concurrent local unlink. The deletion and credential writer also share their file lock. These locks do not constitute a cross-file distributed transaction or prove absence of positions, pending orders, unknown funds or active workers. Exposure-safe unlink and provider readback remain required before BE-004 can be accepted; current low-level local removal must never be described as remote broker closure.

The real source tests exercise independent processes, real files, injected failed rename, stale data, direct-save bypass, current gateway/A4 calls, and a staged real-handler rotation/unlink race. Four custom mutations separately remove the current read, prior-key merge, account serialization and atomic credential swap. Their valid control passes; each induced defect is rejected and source bytes are restored. All 374 inherited mutation identities and 383 edits remain unchanged.

See `../receipts/ACCOUNT_PERSISTENCE_SOURCE_20261022.json` for hashes and measured results. Tests run on Linux; the Windows locking branch is provided but has not been qualified on Windows. No original blueprint/package bytes, new UI, financial permission, provider account, production credential or external host was changed.

Continue with exact OAuth state/broker/device ownership, callback collision/process recovery, authoritative live/demo/read-only account identity and exposure/lease/funds-safe unlink. Provider matching, credential verification/rollback and CEX/funding requirements remain in the same canonical units; this milestone retires none of them.
