## Binding entry and exit rules

The owner directive requires the complete backend first, not merely the backend of the next screen. All34 BE units and all6 BQ units must feed BG-001. All new UX/frontend units, including visual components, prototypes, renderer and navigation, depend on BG-001. Before that, early integration uses headless real service contracts. No temporary UI exemption exists.

Every code-bearing packet requires independent PRE-003 F15, an approved bounded contract, current dependency receipts and resolved start-blocking owner decisions. Every packet completes in full and supplies positive/negative/recovery evidence. The first backend consolidation qualifies its no-loss oracle. Backend receipt tests cannot demand a not-yet-built new UI; they use the genuine service path and qualified existing test authorities.

BG-001 requires every mandatory service/rail, actual producer/caller/readback and coherent frontend consumption bundle. Mock-only integration, placeholders, wrong-source receipts, “partial” implementations and arbitrarily unsupported mandatory capabilities fail. F15 and backend completion do not grant live financial actions or final device acceptance.

Every frontend feature must implement all mapped states, controls and outcomes in the locked design. Full UI coverage is independent of which journeys are convenient to demonstrate. Backend changes reopen BG-001. Final S24/device/visual proof, release authorization and legacy retirement remain separate and mandatory.

Document hashes are not signatures. Prepared locks and this generator cannot issue owner approval, F15 or Backend Complete. The runtime verifier must validate real trusted issuer signatures, source/scope/expiry and all required receipt bindings.
