# Whole-Backend Complete contract — BG-001, Rev 1.11

## One global frontend entry gate

BG-001 is the only gateway into new native UX, visual prototypes, theme, orb/chart renderers, app shell or frontend implementation. Every required backend capability is included, not merely those consumed by the first screens. Its exact set is the 74 backend IDs and 10 backend-verification IDs in `plan/DEVELOPMENT_PLAN.json`. Logical service units do not prescribe separate deployable microservices. Forecast component qualification supplies evidence to this gate, never an alternative frontend authorization.

**Entry:** the independently issued project/source-bound PRE-003 F15 certificate is current; all required backend units are FULL, independently evidenced and integrated; all shared consumers and failure/recovery paths have passed. Requirement/source identity and economic correctness take precedence over a count of passing tests.

**No waiver:** fixtures, documentation PASS, source indexes, an old CI run, a single green happy path or a UI showcase are not completion. A genuine certificate covering a strict subset of required services is invalid. Every requirement and accepted action must be traced through the actual registered producer, state store, caller, effect and readback.

## Bound scope and evidence

A BG certificate binds project ID; canonical blueprint, plan, scope-lock and source/dependency hashes; deployed backend configuration and all consumer-contract revisions; exact required capability IDs and their operation-contract digests; every required test/result receipt; independent issuer identity and verification policy; issue/expiry/revocation data; and all unresolved or external findings. Missing, stale, duplicate, mismatched or self-issued evidence is refused.

Signature verification is performed against the independently established DIAL trust store, not a public key supplied inside the certificate, a `signature_valid` flag or the developer's self-report. This package contains no issuing credential. Its NOT_ISSUED templates cannot be promoted by running a documentation checker. The portable readiness check refuses them until genuine signed artifacts are furnished.

F15 certifies the design/implementation preparation and declared external qualification matrix. BG certifies actual whole-backend completion within the explicitly admitted deployment target. Neither grants live orders, funds movement, provider access or Android release authority.

## Complete consumer catalogue

BE-032 exposes a versioned capability/action catalogue: operation and subject IDs, account/strategy/source scope, input/output schemas, state machines, source freshness, eligibility/refusal reasons, required owner proof, event cursors, outcome lookup, privacy and display-field semantics. It includes account/funds, risk/lockout scopes, pending-order/position outcomes, model/strategy development, forecast/uncertainty, event research labs, all Work/Memory/Automation/Browser/Voice/Muse/ARTEMIS controls and other preserved functions.

Headless consumers exercise every supported operation and denial path before UX begins. A backend field being serializable does not prove the correct client actor can call it, an owner action can be executed, or a false result is rejected. No generated-client or fixture shortcut substitutes for the real service registration and actual permitted provider path required by that capability.

## External qualification and no-procurement boundary

Forecast/model/contract research software is implemented in full with admitted existing data or labelled scenarios, as directed. There is no new subscription, license procurement, provider account creation or live prediction-market order sender in this programme. A research-only lab can be qualified for its declared offline/replay purpose without claiming live-market admission.

An operation whose target contract requires a real broker/payment sandbox, data feed, provider receipt or other actual external behavior remains NOT_QUALIFIED until that evidence exists. It cannot be silently reclassified as offline to pass BG. Unrelated backend engineering can proceed in dependency order, but BG cannot waive an unresolved mandatory integration in the approved target. An explicit owner-approved scope amendment is required to change the target, with new evidence and no deletion of historical obligations.

## Reopening and frontend feedback

Detailed native UX begins only after BG. Backend interface ergonomics and domain semantics are specified/tested beforehand; these are not UI prototypes. Once UX begins, a genuinely missing backend capability, changed authority or incompatible contract reopens BG, updates the source/scope fingerprints, invalidates affected receipts and pauses affected frontend work. Implement and requalify the backend change before resuming. No domain logic is hidden inside a screen to keep an obsolete gate green.

## Required falsification cases

Delete a backend unit or operation, remove an inherited owner action, omit forecast component evidence, forge a result, change a source hash, revoke a grant, submit a stale provider receipt, substitute synthetic cash settlement, relabel an incomplete backend unit as frontend, or add a UX prerequisite path that bypasses BG: the applicable validator and real promotion check must refuse. Every refusal has an evidence ID and reason. This document specifies those obligations; it does not certify their runtime implementation.
